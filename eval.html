✦ Eval Framework

Eval Requirements, Criteria, Success Measures, and LLM-as-Judge Design

Companion to the technical architecture. How we measure whether the audit is good enough to ship, how we decide what to do when it isn't, and how an LLM judge fits into the closed-loop improvement system.

The PRD names "Eval & Quality Framework" as a P0 requirement and the gating event for in-product external surfacing. This document operationalizes that P0 — it is the eval design that decides whether V1 can leave CSM-only briefing and reach customers. Numbers in thresholds are recommended starting points based on the PRD's quality posture; AI Science should sign off on final values before pilot.

Why eval is the gate, not the test

The PRD makes two commitments that only an eval framework can enforce:

  1. "Quality over latency & cost for V1." Without measurement, "quality" is rhetoric. The eval defines what quality is, in numbers.
  2. "Trust at scale requires measurable quality." The Eval Framework row in the PRD is the only thing that lets the audit cross the threshold from CSM-only to customer-facing. Without it, in-product launch is a faith bet.

The audit has three failure modes that ordinary AI-feature evals don't catch:

  • Confident wrongness. The agent grades a dimension B but the right answer is C. The customer acts on a wrong root cause and trust collapses.
  • Hallucinated specificity. The agent claims "past purchasers convert 3.2× higher" when the actual number is 1.2× — or worse, when no past-purchaser segment exists. Citation looks credible; underlying number is fabricated.
  • Inconsistency on stable inputs. Two audits run a day apart on the same data return different grades or different actions. CSMs notice immediately; customers do too.

An eval that catches all three needs three layers: per-skill correctness, system-level consistency, and customer-outcome lift. Layered, not picked.

1. Eval requirements

1.1 Coverage requirements

Every audit-producing component must be evaluable, with no holes. The architecture has 16 net-new skills (10 dimension + 3 composition + ≥3 action-execution). Every one of them needs:

  • An input contract — typed inputs with explicit data-availability flags, so eval cases can construct partial-data scenarios deterministically.
  • An output contract — typed outputs that include grade, finding, evidence with citations, root cause, data-availability, and any structured payloads (action chips, deep-link state).
  • At least one ground-truth set — accounts where the right answer is known (expert-CSM-graded), and at least one synthetic-stress set (deliberately broken inputs to test abstain behavior).

Coverage gaps that disqualify the audit from pilot launch:

  • Any of the 10 dimension skills lacking ≥20 ground-truth cases.
  • The action synthesizer lacking a ranked-actions ground-truth set (expert-CSM action lists for ≥10 accounts).
  • Any retrieval tool lacking a freshness/staleness test fixture.
  • No abstain-behavior test (synthetic data-unavailable case for at least 3 dimensions).

1.4 Eval cadence

  • Pre-merge per skill — every change to a dimension skill, the action synthesizer, or a retrieval tool runs the relevant golden-CSM and synthetic-stress subsets. Block merge on regression beyond defined deltas (see thresholds).
  • Daily full-suite — full eval suite against the replay-consistency set; alert on consistency drops or hallucination-rate creep.
  • Weekly outcome review — outcome-tracking set growth + customer/CSM VOC review; new adversarial cases land in the VOC set the same week.
  • Quarterly recalibration — golden-CSM set refresh, judge calibration check (see §5.4), threshold review based on cumulative outcomes.

3.3 Per-merge regression gates

Continuous-integration thresholds for any code change touching skills, prompts, or retrieval tools.

  • No regression > 2 percentage points on per-dimension grade accuracy vs. last green build.
  • No regression on consistency below 0.05 Jaccard delta.
  • Zero new hallucinations on a held-out 50-case canary set.
  • Aggregator determinism must remain at 100% (any drop blocks merge).

4. Decision-log protocol

Eval results without decisions are exhaust. Every eval run that touches a launch gate produces a decision-log entry. Decision-log is structured, dated, and linked to the eval run that triggered it.

4.1 Pass paths

When all gates are in Pass band:

  • Decision-log: "Proceed" — name the launch step that's authorized.
  • Capture: which datasets the eval ran on, which thresholds were tested, who signed off.
  • Even on a Pass, log the weakest three metrics — these become next quarter's improvement focus.

4.2 Warn paths

When ≥1 metric is in Warn but none are in Fail. The decision is not "ship anyway" or "block." It's "contain blast radius and prove out fast."

  • Required containment moves:
    • Reduce pilot cohort size by 50% (e.g. 8 CSMs instead of 16).
    • Add a human-in-the-loop checkpoint: every audit reviewed by AI Science or a senior CSM before sharing with a customer.
    • Increase eval cadence from weekly to twice-weekly during the warn-state period.
    • Set a 4-week reassessment date; if not in Pass by then, reclassify as Fail.
  • Required decision-log entry: name the warning metric(s), the hypothesis for cause, the remediation tried, and the date for reassessment.
  • Specific common cases:
    • Action Jaccard in Warn but grade accuracy in Pass. Likely the action synthesizer is not deduplicating well across dimensions. Targeted fix.
    • Citation validity in Warn but hallucination rate in Pass. Likely a structured-output schema issue. Tighten the JSON schema constraint and re-eval before further rollout.
    • Consistency in Warn for one dimension only. Likely temperature setting on that skill, or under-specified prompt — prompt-tighten and re-eval.

4.3 Fail paths

When ≥1 metric is in Fail band. Launch blocked, period.

  • Required moves:
    • Pause any active rollout (revert to internal-only).
    • Root-cause within 5 business days; remediation owner named.
    • No incremental rollout while in Fail — re-eval to Pass before any progress.
    • If two consecutive fail-then-fail cycles on the same metric, escalate to leadership for scope review.
  • Required decision-log entry: failed metric(s), root-cause hypothesis, remediation plan with named owner and target date, post-fix re-eval plan.
  • Specific common cases:
    • Hallucination rate > 5%. Almost always retrieval-grounding is loose. Tighten evidence-citation contract; reduce LLM creative latitude on findings; consider a separate grounding pass before generation.
    • Worst-dimension accuracy < 60%. Specific dimension prompt or data plane is broken. Isolate the dimension, fix it, re-eval that dimension only first.
    • Aggregator non-deterministic. Code bug, not LLM issue. Aggregator must be code, not prompt — fix immediately, this is non-negotiable.
    • Serious-impact false negative. Stop everything. Add the failure case to the synthetic-stress set permanently; root-cause why the relevant skill missed it.

5. LLM-as-judge: design and use

5.1 When to use LLM-as-judge (and when not to)

LLM-as-judge is right for scale-bound qualitative grading — relevance, faithfulness, root-cause quality, hallucination, action specificity. It's wrong for determinism, exact-match, or numerical correctness — those need code-eval (deterministic checks).

Eval typeUse LLM judge?Reason
Hallucination rateYesRequires reading the finding + retrieved evidence and judging whether the claim is grounded. Scales beyond human review.
Citation validityPartial — judge for "does the citation actually support the claim"; code-eval for "does the citation tuple resolve to a real data point"Two different checks; different tooling.
Action relevanceYes, with calibrationJudge can rate "is this action specific to this account?" against the customer context and dimension findings.
Root-cause qualityYes, with calibrationJudge can compare diagnostic chain to expert-equivalent reasoning.
Grade accuracy vs. expertNo — exact-matchJust compare strings.
Aggregator determinismNo — code-evalByte-identical check.
Deep-link surface-loadNo — synthetic click testBehavioral, not qualitative.
Consistency (rerun similarity)No — Jaccard on action setsSet arithmetic.
Customer-outcome liftNo — A/B + stat-sig testCausal inference, not grading.

5.2 Architecture

Three judges, each with one job. Specialization beats omniscience in LLM-as-judge — narrow judges with explicit rubrics outperform a single general-purpose judge.

JudgeInputOutputUsed by
FaithfulnessJudgeFinding text + retrieved evidence bundle (citations + raw values from data plane)Per-claim verdict: {supported, unsupported, partially-supported} + reasonHallucination rate, citation validity
RelevanceJudgeAction card + dimension findings + customer context (vertical, ICP, brand voice)4-axis score (1–5): {specificity, executability, leverage, on-brand} + reasonAction relevance, ROI calibration
RootCauseJudgeDiagnostic chain on a Moderate/Needs-Attention dimension + supporting evidence4-pt score on causal-chain coherence + alt-hypothesis flag if a more likely cause is supported by the same evidenceRoot-cause quality

Why three judges, not one. A unified judge tends to anchor on the most prominent failure mode (usually hallucination) and under-weight the others. Three narrow judges, each with their own rubric and few-shot calibration set, produce more reliable grades. Costs more compute; worth it for V1 quality posture.

Judge model selection. Use a strong model for the judge — stronger than the agent itself if affordable. The judge's whole value is being more rigorous than the system being judged. Use a different model family from the agent (avoids same-family bias). Prefer Claude Opus or equivalent for the judge if the agent runs on a smaller model.

5.3 Judge prompt design

Four design rules for judge prompts that make them measurably better than generic "rate this on 1–5":

  1. Anchored rubric, not abstract scale. Each score level has a concrete behavioral definition, with a worked example. "5 = action references a specific account-level data point AND names the Mailchimp surface AND has executable steps. 1 = generic advice that could apply to any account."
  2. Pairwise comparison when possible. Judges are more reliable comparing two outputs ("which is more grounded?") than scoring one in isolation. Use pairwise for action quality especially.
  3. Mandatory cite-the-evidence. Judge must quote the specific span of evidence (or specific data tuple) supporting its verdict. No quote → automatically Warn.
  4. Explicit "I cannot determine" path. Same abstain-as-first-class principle as the audit itself. If the judge can't confidently rate, it returns insufficient-evidence — better than a guessed score.

Judge prompt template (FaithfulnessJudge — illustrative):

You are an evidence-grounding judge for a Mailchimp campaign-audit agent.

Your job: given a FINDING and the EVIDENCE the agent had access to,
classify each quantitative or specific claim in the finding.

Categories:
- supported: the claim is directly entailed by an evidence tuple
  (you must quote the supporting tuple)
- partially-supported: the claim is directionally true but the
  specifics (numbers, time windows, segment names) are not
  exactly entailed by evidence
- unsupported: the claim is not present in evidence
- insufficient-evidence: you cannot determine from what was
  provided

Output schema (JSON):
{
  "claims": [
    {
      "text": "",
      "verdict": "supported | partially-supported | unsupported | insufficient-evidence",
      "supporting_evidence_tuple": "",
      "reason": ""
    }
  ]
}

Be strict. If the finding says "past purchasers convert 3.2x higher"
but evidence shows the multiplier is 2.8x, that is partially-supported,
not supported. Numbers matter.

FINDING:
{finding_text}

EVIDENCE:
{evidence_bundle}

Determinism for judges. Run the judge with temperature=0 and a fixed seed where supported. Judge variance is its own failure mode; on the calibration set the judge should grade the same finding the same way ≥95% of reruns.

5.4 Calibration

An LLM judge is only as trustworthy as its calibration. Required calibration steps:

  • Calibration set: 50 expert-graded findings with known verdicts (mix of supported, partially-supported, unsupported). Quarterly refresh.
  • Calibration metric: Cohen's κ between judge and expert. κ ≥ 0.7 is the bar to deploy a judge. Below that, judge is no better than coin-flip on edge cases.
  • Drift detection: Daily rerun of a 20-case canary calibration set. Alert on κ drop > 0.05.
  • Adversarial calibration: Include 5 "trick" cases in calibration — e.g. a finding with a citation that looks right but cites a different period than claimed. Judge must catch these.

Don't trust uncalibrated judges. A well-prompted judge that hasn't been measured against expert ground truth is exactly as reliable as the agent it's grading — which means using it as a gate is circular. Calibration is the only thing that gives judge scores enforceable authority in launch decisions.

5.5 Pitfalls to avoid

Common failure modes when wiring LLM-as-judge into an eval system:

  • Same-model judge. Judge and agent share weights → judge inherits the agent's blind spots. Use a different model.
  • Length bias. Generic LLM judges over-reward long, well-formatted outputs. Mitigate with explicit "verbosity is not quality" instruction + length-controlled comparison cases in calibration.
  • Position bias. In pairwise comparisons, judges anchor on whichever option appears first. Mitigate by running each comparison in both orders and averaging.
  • Confidence-without-grounding. Judges asked to rate on a 1–5 scale will produce a confident number even with no information. The mandatory-cite-the-evidence rule + explicit "insufficient-evidence" path is what defends against this.
  • Drift after model upgrades. When the judge model is upgraded, calibration must be redone. A new judge model is a new judge.
  • Using the judge to fix itself. Don't use the judge's own scores to retrain the agent without an independent human review of the judge's decisions on a sample. Otherwise you optimize for the judge, not for customer outcomes.

6. Closed-loop improvement: how the eval drives the agent

The eval system isn't just a gate; it's the steering wheel for improving the agent. The closed loop has four feedback paths:

  1. Hallucination signal → grounding-prompt tightening. When FaithfulnessJudge κ drops or hallucination rate creeps up, the response is to tighten the structured-output schema (require evidence-tuple before claim) or to add a separate "grounding pass" that asks the agent to extract evidence first, then write the finding citing it. Track whether this fixes the regression in next eval cycle.
  2. Action irrelevance → action-synthesizer rewrite. Low Jaccard vs. expert + low specificity scores = the action synthesizer is generating generic advice. Common fixes: include more customer-context in its prompt, deduplicate aggressively across dimensions, force ranking by leverage not by which dimension surfaced the issue.
  3. Inconsistency → temperature / prompt determinism review. If consistency drops, audit which skill is flaky. Usually a prompt that allows interpretation latitude. Tighten prompt, lower temperature on that skill specifically. Re-eval consistency.
  4. VOC-flagged failures → adversarial set growth. Every customer-flagged "this finding was wrong" gets added to the VOC adversarial set. Pre-merge eval includes the adversarial set; this means each known failure mode is regression-protected forever after.

Cadence rule. Eval results without action are wasted. Every weekly eval review must produce one of: a fix landed, an experiment scoped, or an explicit "we're accepting this for now and here's why" decision-log entry. No item sits in eval-output limbo.

Summary (one screen)

  • Three measurement layers: per-skill correctness, system-level consistency, customer-outcome lift. Layered, not picked.
  • Five datasets: golden-CSM, synthetic-stress, replay-consistency, outcome-tracking, VOC-adversarial. Each owned, each refreshed.
  • Seven quality axes: dimension accuracy, hallucination rate, citation fidelity, root-cause quality, action relevance, ROI calibration, consistency.
  • Two-tier thresholds: pilot-launch (CSM/AM Briefing) and GA-launch (in-product). Pass/Warn/Fail bands with explicit decisions for each.
  • Decision-log discipline: every gate produces a structured decision-log entry. Warn = contain blast radius. Fail = block + named remediation owner.
  • Three LLM judges, calibrated to κ ≥ 0.7: FaithfulnessJudge, RelevanceJudge, RootCauseJudge. Anchored rubrics, mandatory evidence-citation, explicit abstain path.
  • Closed-loop improvement: eval signals route to specific remediation paths. VOC failures become regression cases. Every weekly review produces an action.
  • The single most important property: quality is measurable, not asserted. The PRD's "trust at scale requires measurable quality" line is what this whole document operationalizes.
