Technical Architecture

Net-new skills, tools/APIs, and runtime context patterns required to build the audit on top of Mailchimp's Analytics Agent infrastructure.

Source material: PRD (PRD: MC AI Campaign Health Intelligence, Stephen Yu) + Vision Prototype (campaign-audit/Design Bench.html).

Audience: Eng + AI Science + PM, ahead of leadership shareout.

Status: Research/architecture deliverable. No code changes proposed in this document — it is the answer to the three questions:

  1. What net-new skills are required, what problem each solves, and why it matters.
  2. What additional tools / APIs / data (ALF labels, segmentation data, etc.) are needed.
  3. Whether we need new context beyond what we have today, or whether retrieval/composition needs to change at runtime.
This document is derived from the PRD, the prototype's UI contract, and reasoned inference from Mailchimp's existing Analytics Agent architecture. The local workspace does not contain the production Analytics Agent codebase — only adjacent prototypes (Klav-Intel, Hub-Intel, CI-Agent, the static analytics-ai prototype). Where I cite an existing system (BigQuery, StarRocks, MTA, ALF, MCDS, Customer Journey Builder), I am inferring it exists from the PRD's "Reuses Analytics Agent retrieval/eval infra" line and team common knowledge — eng owners must validate before commitment. Items marked [from PRD] or [from prototype] are certain. Items marked [inferred — verify] need confirmation.

Context

What the prototype commits to producing

A campaign-detail surface inside the Mailchimp app shell that renders, in one screen:

  • An overall A−C grade with a one-line verdict and status counts (Strong / Moderate / Needs attention / No data).
  • 10 dimension findings, each with a status pill, a customer-language question, and a one-line headline finding.
  • 5 (target: 5–7) ranked actions with Effort × Impact × Time-to-Results chips, linked dimension, and an in-product CTA (e.g., "Save as template," "Build segment") that deep-links into Mailchimp.
  • A "How this was generated" tab with: data sources audited, explicit gaps that were not audited, dimension weights (with a compliance floor), and a methodology + disclaimer.

Why this matters for architecture

Each prototype element is a runtime contract on the agent. Per-dimension grades require per-dimension evidence retrieval. Action chips require Effort/Impact/Time scoring per recommendation. Deep-link CTAs require structured action payloads with target surface + prefilled state. The "What we couldn't audit" panel requires explicit data-availability flags propagated end-to-end. These are not free.

What the PRD commits to

Quality-over-latency in V1; deterministic evidence-backed scorecards; abstain-when-unsure; root-cause diagnosis on Moderate/Needs Attention; omnichannel by default (email + SMS + automation); CSM/AM Briefing surface first, then in-product self-serve; "Take this action" deep-links in V1, "Do this for me" approval-first execution in V1.5 (cross-team dependency).

The architecture choice that flows from this

A planner-orchestrator agent that decomposes "audit this campaign / portfolio" into ~10 parallel dimension subtasks; each subtask is a deterministic skill calling typed tools against Mailchimp's data plane; results are aggregated into a structured AuditReport with confidence flags; a separate Action Synthesis skill consumes all dimension findings and emits ranked, deep-linked actions. Consistent with the PRD's "Reuses Analytics Agent retrieval/eval infra" line and with the Bedrock/MCP tool-use model.

1. Skills (the new units of agent behavior)

A "skill" here = a goal-bounded unit that the planner can invoke; internally it calls one or more typed tools and returns a typed output. Skills are the right granularity for the audit because each dimension has a distinct retrieval pattern, distinct evaluation logic, and distinct failure modes.

Layered model. Three tiers of skill:

  • Audit-Dimension skills (10) — each grades one dimension, returns {grade, finding, evidence[], rootCause?, dataAvailability}.
  • Audit-Composition skills (3) — orchestration, aggregation, action synthesis; consume dimension outputs.
  • Action-Execution skills (V1 vs V1.5) — V1 deep-links; V1.5 constructs Mailchimp changes for approval. Cross-team-dependent.

Why "skills" not "prompts"

  1. Eval granularity. The PRD's eval harness scores dimension accuracy, hallucination rate, ROI calibration, and consistency per dimension. That requires per-dimension evaluable units with typed inputs/outputs. A monolithic "audit prompt" isn't evaluable at the dimension level.
  2. Failure isolation. If the SMS data plane is down, CrossChannelCoherenceSkill should return dataAvailability: partial and the audit continues; the other 9 dimensions shouldn't be poisoned. Skill-level isolation makes this clean. A monolithic prompt cascades failures.

Why "abstain" is a first-class skill behavior

The prototype renders No data as a status pill alongside Strong/Moderate/Needs Attention. That's only credible if every skill emits dataAvailability: {full | partial | none} and the skill refuses to grade when retrieval falls below a confidence threshold. This is not a UI veneer; it's a contract every skill must implement. The PRD calls this out explicitly ("the agent appropriately abstained from scoring on dimensions with partial or missing data, marking them transparently rather than hallucinating").

1.2 Audit-Composition skills (3) — net new

SkillSolvesWhy it matters
AuditPlannerSkillDecomposes the user/CSM ask ("audit this campaign" / "audit last 90 days") into a per-dimension execution plan, choosing weight + depth based on context (single campaign vs portfolio).The PRD's "audit flexes to the unit of analysis" requires a planner that selects scope, time window, and per-dimension depth. Without this, every audit is the same.
OverallGradeAggregatorSkillRolls up 10 dimension grades into the A−C overall + one-line verdict + status counts.The prototype's "How this was calculated" tab commits to specific weights (Performance + Deliverability = 30%, Audience + Conversion + Cross-Channel = 30%, Offer + Creative + Timing = 25%, Intent–Outcome = 10%, Compliance = 5% with a floor). Must be code, not LLM prompt, for determinism. The "compliance floor" specifically requires deterministic rule logic — an LLM rolling this up is a hallucination vector.
ActionSynthesizerSkillReads all 10 dimension findings + customer context, emits 5–7 ranked actions with Effort × Impact × Time-to-Results chips, ROI directional language, target Mailchimp surface, and prefilled deep-link payload.The highest-leverage skill in the system. The audit's value depends on actions. Must (a) deduplicate across dimensions, (b) prioritize by leverage not by which dimension found it, (c) generate executable Mailchimp steps not generic advice, (d) emit a deep-link payload the UI can route. Most attacker-able for hallucinated ROI — gate quantitative ROI behind calibration evidence.

Architectural pattern. Planner runs first → fans out to 10 dimension skills in parallel → results stream into the Aggregator (deterministic rule code) → results + customer context feed the Action Synthesizer (LLM with structured output) → final AuditReport is rendered.

3. Context — new sources, new composition, or both

3.1 New context types beyond what the Analytics Agent has today

The Analytics Agent today is built for ad-hoc Q&A: a customer asks a question, the agent retrieves the slice of data needed, returns an answer. The Audit is categorically different — it's proactive, comprehensive, multi-dimensional, and prescriptive. Three new context types are required:

(a) Cross-campaign context (corpus-level, not single-campaign)

The prototype's Action #1 ("save this campaign as a Gift Guide template — your top revenue broadcast in 90 days") and Dim 3 ("patterns across your own winning subject lines") require the customer's full campaign history in retrieval scope, not just the campaign under audit.

  • What to build: A campaign-corpus retrieval mode that pulls last N (~90–180 days) of campaigns into a single retrieval window, indexed by performance + content embedding for similarity / pattern queries.
  • Composition change: New CorpusContext block in the system prompt — feeds Dim 3, 5, 6, 8, 10. Without it, "patterns in my own winners vs. losers" is impossible.

(b) Customer-voice / qualitative context

Dim 9's headline content is unsubscribe-reason themes with verbatim quotes. This is qualitative, NLP-derived context the existing Analytics Agent likely doesn't surface — its job is metrics, not free-text clustering.

  • What to build: A free-text clustering pass over unsub reasons, "I didn't sign up" complaints, and spam-complaint content, themed and quantified, with verbatim quote selection.
  • Composition change: New CustomerVoiceContext block — this is the prototype's most differentiated data surface, the one customers say "I've never seen this before."

(c) Brand-and-account context (always present, never optional)

For an audit to read "personalized, on-brand," every dimension's narrative needs the customer's brand voice + account context as ambient context.

  • What to build: A CustomerProfileContext block — C1 profile + brand voice + plan tier + vertical + lifecycle stage — assembled once per audit, injected into every dimension skill's prompt.
  • Composition change: Lift this from on-demand retrieval to per-audit pre-fetched ambient context. Cheap and high-leverage.

3.2 New retrieval / composition patterns

Three runtime changes in how context is retrieved and composed:

(i) Context budget per skill, not per turn

Today's pattern (assumed): one user question → one retrieval pass → one LLM call. The audit fans out into 10 dimension skills running in parallel; each needs its own focused context bundle, not the union of all retrievals. This means a context-router that selects the right slice for each skill (e.g., DeliverabilityListHealthSkill gets ISP-level deliverability + suppression + bounce trend; not subject-line embeddings). Saves cost and reduces prompt cross-talk.

(ii) Pre-fetched ambient + skill-specific dynamic

Pattern: Planner pre-fetches CustomerProfileContext + CampaignPortfolioContext once; each dimension skill is invoked with (skill_query, ambient_context, dimension_specific_context). This is a small but real change — today's pattern is likely all-dynamic per call.

(iii) Evidence-citation discipline at every skill output

The prototype's "Generated by AI" pill + "Each finding cites a specific data point" methodology copy commits to citation-grounded output. Every finding string returned by a skill must come with evidence: [{metric, value, period, source_table}] so the UI can show "why this finding." Without this, the "How this was generated" tab is theater. This is a structured-output requirement (JSON schema enforcement at the LLM layer) more than a retrieval change, but it's the runtime-composition discipline that makes the trust mechanic work.

3.3 Context governance

Three discipline items for the leadership shareout:

  • Data-availability propagation. Every retrieval call must return dataAvailability: {full | partial | none}; every skill must propagate it; the Aggregator must surface it as the No data pill in the UI. End-to-end, not just at the prompt layer.
  • Stale-data guards. Audits cite specific data points by date. If retrieval returns stale data (cache miss masquerading as fresh), the audit is wrong but confident. Audits should fail closed when freshness < threshold rather than silently using stale data.
  • PII / privacy posture for unsub reasons + verbatim quotes. Dim 9 quotes customer free-text. PII redaction must be in the retrieval pipeline before the LLM sees it, not bolted on after.

Verification — how to test the architecture end-to-end

(How any team would prove this works before the leadership shareout — these are checks, not implementation steps.)

  1. Skill-level eval. Run each of the 10 dimension skills against a curated set of 10 pilot accounts; compare to expert-CSM ground truth on dimension grade, root-cause quality, and citation accuracy. Per-dimension F1 + hallucination rate.
  2. Aggregator determinism. Feed identical dimension-skill outputs through the Aggregator 100 times; confirm grade is byte-identical (zero LLM, all rule logic).
  3. Action synthesis A/B. Run ActionSynthesizerSkill on the same dimension outputs across 3 runs; confirm action-set Jaccard similarity ≥ 0.8 (consistency under stable inputs is a P0 eval criterion in the PRD).
  4. End-to-end abstain test. Inject a synthetic SMS-data-unavailable case; confirm CrossChannelCoherenceSkill returns dataAvailability: none, the dimension renders No data, the audit completes successfully, and the action list does not reference SMS.
  5. Deep-link contract test. For each action type (segment / suppression / template / journey / A/B / inbox-preview), click the deep-link and confirm the Mailchimp surface opens with prefilled state.
  6. PII guard test. Feed an unsub free-text containing email + phone; confirm the redaction pipeline strips before the LLM sees it.
  7. Latency floor. Per PRD, V1 prioritizes quality over latency; still, set a 5-minute ceiling for back-end pilot runs and confirm.

Open questions for the leadership shareout

  1. Does the existing Analytics Agent retrieval layer expose customer-corpus retrieval (last 90–180 days as a single window), or is it single-question-shaped? Determines whether CampaignPortfolioContext is a retrieval-config change or a new pipeline.
  2. Are SMS + automation aggregate signals join-able with email at the campaign / portfolio level today (not just deliverability metrics)? Determines whether CrossChannelCoherenceSkill is feasible in V1 or must be deferred. Already an open question in the PRD; this architecture can't proceed without resolution.
  3. Is the C1 profile from AI Science delivering by pilot date, with brand voice + ICP + vertical? Without it, every dimension reads generic. The PRD calls this out softly; it should be elevated to a named risk with a delivery commitment.

Recommendation summary (one screen)

  • Net new skills (16 total): 10 Audit-Dimension + 3 Audit-Composition + 5 Action-Execution (V1.5+, cross-team-dependent). V1 ships with 10 + 3 + DeepLinkActionSkill.
  • Net new tools (≈14): Reuse existing Mailchimp data-plane where possible. The high-gap items are getSegmentLift, getUnsubReasons (free-text), SMS+automation joined retrieval, render test data, C1 profile, ALF labels at three granularities. Path A (LLM classifier as fallback for missing ALF labels) keeps V1 shippable.
  • Net new context types (3): Campaign-corpus context (for cross-campaign pattern detection), CustomerVoice context (free-text NLP for Dim 9), pre-fetched CustomerProfile ambient context (for personalized tone).
  • Net new retrieval/composition patterns (3): Per-skill context routing, ambient + dynamic split, evidence-citation discipline as a structured-output requirement.
  • The architectural choice that matters most: Skill-per-dimension with abstain-as-first-class-output. This is what makes the prototype's "No data" pill and "How this was generated" tab credible at scale, and it's the single biggest difference between the existing Analytics Agent's Q&A pattern and this Audit pattern.
